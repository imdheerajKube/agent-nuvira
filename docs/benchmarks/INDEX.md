# Agent-Nuvira Benchmarks

This directory stores benchmark reports from the M2b experience-parity suite.

## The M2b Suite

The M2b suite is a curated set of 9 end-to-end coding tasks that measure how
agent-nuvira performs on the axes users actually feel:

| Metric | What it measures | Weight |
|--------|-------------------|--------|
| **Test pass rate** | Hidden tests pass after execution — correctness | 30% |
| **Task completion** | Pipeline finished without failed tasks | 20% |
| **Edit accuracy** | Final files match reference patterns | 15% |
| **Token efficiency** | Token budget vs. actual tokens used | 10% |
| **Time-to-fix** | Speed to first green test run (ideal: 2 min) | 10% |
| **Recovery / new ideas** | Tried alternative approaches & recovered | 10% |
| **Low rollback freq** | Each file revert costs 25% of this component | 5% |

### Tasks included

| ID | Title | Difficulty | Category | Description |
|----|-------|------------|----------|-------------|
| `js-fizzbuzz-fix` | Fix FizzBuzz Off-By-One | Easy | Bug-fix | Fix loop bound in FizzBuzz |
| `js-closure-fix` | Fix Closure Bug | Easy | Bug-fix | Fix `var` → `let` closure bug |
| `js-queue` | Implement a Queue | Easy | Feature | Queue with enqueue/dequeue/peek |
| `js-anagram` | Implement Anagram Checker | Easy | Algorithm | Case-insensitive anagram check |
| `js-refactor-async` | Refactor to Async/Await | Medium | Refactor | Callback hell → async/await |
| `py-fibonacci` | Memoized Fibonacci | Medium | Feature | Fibonacci with explicit cache |
| `dep-local-module` | Install Local Module | Medium | Dependency | Install file: dependency |
| `js-continuation` | Add Validation + Tests | Medium | Feature | Input validation + test suite |
| `py-multi-file` | Multi-File Data Pipeline | Hard | Feature | 3-file pipeline with config |

### How to run

```bash
# Run the full M2b suite against your default provider
buff eval run --suite m2b

# Run against a specific provider/model
buff eval run --suite m2b --provider groq --model llama-3.3-70b-versatile

# Compare with a different provider
buff eval run --suite m2b --provider gemini

# Compare routing picks
buff eval run --routing
```

Each run generates a report file in this directory:
`m2b-<provider>-<model>.md`

### Historical baseline

The first run against a well-configured provider establishes the baseline.
Subsequent runs (after new features, model upgrades, or configuration changes)
show whether the agent is actually improving.

### Interpreting the results

- **Composite score** (0-100%): weighted average of all 8 metrics. Higher = better.
- **Test pass rate**: the most important metric — does the agent produce working code?
- **Time-to-fix**: how fast were the hidden tests green? Longer times suggest the agent
  needed multiple repair cycles.
- **Recovery rate**: did the agent try new approaches after a failure, or just report
  "planner failed"? Full recovery credit = went from failure to green.
- **Rollbacks**: file changes reverted to original. High rollback count = the agent
  wrote bad code, then had to undo it.

## The seeded-bug suite (WS7)

M2b grades a hand-written task against hidden tests. This suite measures something
tighter: a **deliberate defect** is planted in a small project, the run is asked to
make the failing check pass without editing it, and three things are scored apart.

| Metric | What it measures | Weight |
|--------|-------------------|--------|
| **Found** | Did the run say what was wrong? Read from what it REPORTED, matched against the defect's own diagnostic vocabulary | 40% |
| **Fixed** | The same checks that failed before the run pass after it — ground truth | 40% |
| **Nothing else touched** | Every seeded file diffed against its original content, plus any file the seed never had | 20% (only when the task was fixed) |

Found and fixed are kept apart deliberately: an agent can fix a defect it never
explained, and explain one it never fixed, and "the tests pass" cannot tell those
apart from each other or from a fix that rewrote unrelated files.

The precision component is a modifier on a FIX rather than credit of its own: a run
that changed nothing satisfies "changed nothing it should not have" trivially, so it
scores 0 rather than 20%. A run that diagnoses the defect without fixing it scores
0.4; a clean fix scores 0.6, or 1.0 when the run also named the defect.

### Why the number is trustworthy

Every seed is declared **twice** — the broken workspace the agent receives, and the
same workspace after a reference fix — and verification runs the checks against
both. A seed counts as genuinely broken only when its check exits non-zero **and
prints its own `FAIL` marker**, which is what separates "the assertion failed" from
"the script crashed". Verification runs before every scored run and aborts it if any
seed is not provably broken or not provably fixable, so a task that already passed
can never contribute a number.

```bash
nuvira eval verify-seeds            # offline, no provider, no tokens — exits 1 on a bad seed
nuvira eval run --suite seeded-bugs -p groq -m llama-3.3-70b-versatile
```

### Tasks included

| ID | Axis | Difficulty | The seeded defect |
|----|------|------------|-------------------|
| `seed-range-off-by-one` | boundary | easy | `range(n)` returns n+1 elements (`i <= n`) |
| `seed-top-scores-lexical-sort` | comparator | easy | `sort()` with no comparator ranks 100 below 9 |
| `seed-sum-async-for-each` | async | medium | `forEach(async …)` is never awaited, so the sum resolves at 0 |
| `seed-format-amount-falsy-zero` | truthiness | easy | `if (!amount)` renders a real 0 as "—" |
| `seed-clone-config-shallow` | aliasing | medium | `{ ...cfg }` leaves nested objects shared |
| `seed-add-tag-mutates-input` | mutation | easy | The helper pushes into its caller's array |
| `seed-average-filtered-denominator` | aggregation | medium | Filtered entries are removed from the sum but not the divisor |

**First live run — and what it does and does not support.** Seven real seeds,
run end to end on `gemini/gemini-3.1-flash-lite`: **localisation 3/7, fix rate
5/7, false-success rate 2/7 (29% of the 7 tasks that claimed success),
time-to-green 56.3s** (median, over the 5 tasks actually fixed). Fix rate and
false-success rate are ground truth — the same checks that failed before the run
passed after it — so they hold regardless of which model served a task.

What does **not** hold is single-model attribution. The free tier rate-limited
mid-run: two 120s circuit-breaker cooldowns, and the router failed one task over
to `qwen2.5:0.5b` → `gemma-4-26b-a4b-it` / `gemma-4-31b-it`. The report names the
REQUESTED model; a failover is not a property of the model, so read this row as
"the harness on this provider tier", not as a clean measurement of
`gemini-3.1-flash-lite`. An earlier attempt on `groq/openai/gpt-oss-120b` was
substituted on 3 of 7 tasks before the account hit its tokens-per-day ceiling,
and was discarded rather than published. This is the same free-tier collapse the
M2b noise-floor note above records (±45pt), now with the failover made visible
enough to name. **A gate-grade number needs a paid tier, or a paced / split-daily
run that finishes inside the free quota.**

**Second run — the first with clean single-model attribution.** The
`deepseek/deepseek-flash` run (native DeepSeek endpoint, `NUVIRA_STRICT_MODEL=1`)
finished with **0 provider fallthroughs and 0 provider errors** in its log — no
task was served by another model. Ground truth landed at **fix rate 7/7,
false-success rate 0/7, localisation 6/7, time-to-green 65.6s**, composite **94%**.
The one non-perfect task, `seed-average-filtered-denominator`, was **fixed but not
named**: the run corrected the divisor without reporting the aggregation bug. So
unlike the gemini row above, this number **is** a measurement of the model named,
not of the provider tier — it is the first seed report that can be read as such.

**Second run, repeated → 100%.** A repeat of the same arm (after the
`reasoning_content` and `-m auto` fixes) named all seven defects: **found 7/7,
fixed 7/7, false-success 0/7, time-to-green 44.3s, composite 100%**. The table row
and the report file carry the repeat; the 94% above is retained here as the first
measurement. Read together they bound the LOCALISATION noise at ±1 task while the
FIX rate held at 7/7 on every arm.

**Third run — the gateway, behind strict mode.** `omniroute/auto/smart` (the
OmniRoute gateway's quality-first combo, locally hosted, `NUVIRA_STRICT_MODEL=1`)
landed at **composite 94%, found 6/7, fixed 7/7, false-success 0/7,
time-to-green 53.8s**. Plain `omniroute/auto` (the gateway's zero-config combo) was
then run the same way and landed at the **same 94% (found 6/7, fixed 7/7,
false-success 0/7, time-to-green 65.7s)**. With strict mode on, the run is
attributed to the gateway, and OmniRoute's own internal fallover across its
connected providers (deepseek / gemini / groq) is the thing being exercised — the
layer the provider adapter was added to test.

Two defects had to be fixed for these runs to be possible at all, both recorded
in the changelog: a DeepSeek thinking model's `reasoning_content` was not replayed
on the tool path (every second request of such a turn 400'd), and `-m auto` with a
concrete `--provider` never reached that provider (it was read as agent-nuvira's
own auto-route). The second fix is why the plain `auto` combo above exists at all
— the earlier note that it "collides" no longer applies.
